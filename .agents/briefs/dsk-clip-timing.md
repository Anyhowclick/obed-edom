# DSK clip start timing + visual-order naming — owner decisions (2026-09-16)

Context: the Generator inserts one pure-video clip per FW movie item into the DSK slide (behind the live overlays, dissolve transition). Keynote's AppleScript has no build API and its auto-added `apple:movie-start` build timing is non-deterministic (r16: slide 1 came out On Click, slide 2 After Transition), so timing is written OFFLINE in the assembler post-pass.

Rules (owner, final):
1. VISUAL ORDER everywhere: movie items on a slide are ordered left-to-right by placed x, then y (refuse on a tie). This order drives the clip index MM in `<stem>.NNN.MM(.src).mov`, the ClipResult order, the manifest `srcClips` order, the insertion order, and the build chunk order. One shared helper `visual_movie_order(rects: Mapping[ItemId, Rect]) -> list[ItemId]` in `dsk_movie_export.py` (rects may be FW-space item rects or DSK-space fitted rects; the affine preserves x-order for unrotated items; the assembler asserts FW-order == DSK-order and refuses on mismatch).
2. Timing per DSK slide, keyed by the SOURCE movie's `TSD.MovieArchive.playsAcrossSlides` flag:
   - Continuity movies (source flag True): the leftmost continuity clip → chunk position 0, After Transition, 0 s (`automatic: True, referent: True, delay: 0.0`); every other continuity clip → With Build 1 (`automatic: True, referent: False, delay: 0.0`), placed right after chunk 0. Rationale: each DSK slide now holds an independent clip, so continuing movies must all be playing immediately after the transition.
   - Different movies (source flag False): CASCADE — each one is its own stage after the previous build (`automatic: True, referent: True, delay: 0.0`) at the next chunk position, in visual order.
   - A single-movie slide (any slide, including FW 11's): After Transition, 0 s.
   - `playsAcrossSlides` is written False on EVERY inserted clip. The 0.5 s movie-start effect `duration` is Keynote's own — never change it. Never copy source movie-start builds onto DSK slides.
3. Gold reference for the flag encoding: `/Users/anyhowclick/Desktop/Convert wall to 16x9 CGs/Alpha_DSK.key` slides 6–8 (owner hand-made; read-only, copy before any tool that might write). Read their `KN.BuildChunkArchive` flags offline and match the same encoding. Vocabulary confirmed on the r16 FW deck: `automatic False, referent True` = On Click; `automatic True, referent True` at chunk 0 = After Transition, at pos>0 = After Build N; `automatic True, referent False` = With Build N; `delay` is seconds.
