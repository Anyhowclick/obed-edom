## OPEN 1 — offline-write fallback rate (CHARACTERIZED 2026-09-17; hypothesis overturned)

- **ORIGINAL SYMPTOM:** 704 of 3290 offline-write specs (~21%) fell to the AppleScript fallback;
  126 of 148 slides had `missed>0` (`value_clean=True` throughout — correctness fine; the concern
  was speed + Keynote dependence). The original hypothesis was a *systematic patcher gap* — some
  spec kind the surgical writer refuses and defers — worth extending the patcher to own.
- **FINDING (the hypothesis is WRONG).** Instrumented the patcher to tag every deferred spec with a
  coarse miss reason (`feat/offline-fallback-reasons` @ `5ea2ce2`, per-spec `miss_reasons` aligned
  with `missed_specs` → `run_offline_write` `fallbackReasons`/`fallbackReasonsBySlide` histogram),
  then re-ran the full deck (2026-09-17; reproduced the benchmark exactly — 3822 applied / missed 0,
  zorderGui 0, fallback covered every spec, no unwritable). The 704 misses break down as:
  - **`text-autosize` 427 (61%)** — the writer can't refresh Keynote's autosize `naturalSize` render
    cache offline. (Initially read as fundamental; the RESEARCH below overturns that — the size need
    not be computed at all, only the box repositioned.)
  - **`masked-media` 188 (27%)** — the writer refuses a real crop rather than mis-write it. (Initially
    read as fundamental; the RESEARCH below shows the axis-aligned crop transform already exists.)
  - **`group-needs-keynote:group-residual` 83 (12%)** — residual/rotated groups need live layout.
  - **`group-child-scale` 6 (0.9%)** — the only arguably-closeable family.
  - **`unresolved` = 0** and **`*-resize-unwritable` = 0** — the two "maybe closeable" families
    (addressing/reconcile gaps, editableBezier node rescaling) contributed NOTHING. There is no
    surgical-patcher gap.
  - Worst slides confirm the mix: 123 `{text-autosize 86, masked-media 4}`, 57 `{ta 26, mm 1}`,
    70 `{ta 23, mm 1}`, 103 `{ta 19}`, 135 `{mm 17}`, card-wall 125/127 carry the group-residual +
    child-scale specs.
- **INITIAL CONCLUSION (later revised):** the first read was that ~99% of the fallback is *fundamental*
  classes the writer correctly defers, and the ~21% is not a gap to close. That framing conflated "the
  writer refuses it" with "impossible" — the RESEARCH below shows both dominant classes are recoverable.
- **EVIDENCE:** log `output/bank/2026-09-17/fallback-reasons-run/reasons_run.log` (the `Offline-write
  fallback reasons:` + `worst slides` lines); output deck `~/Desktop/Full_Report_Card_reasons_CG.key`.
  Instrumentation is standing diagnostics — keep it; every future run now emits the histogram. Logic
  lives in `iwa_write._slide_edits` (the `_miss(reason)` tags) and `offline_write._fallback_reason_histogram`.

## OPEN 1 — RESEARCH VERDICTS (2026-09-17; 4 Opus researchers, read-only)

Two researchers per dominant class (a hard-derivation angle + a seed/avoidance/classification angle).
Bottom line: **neither dominant class is fundamental** — but an independent adversarial verify
(2026-09-17) tempered both PASS verdicts to CONFIRMED-WITH-CAVEATS and found the first-pass experiments
**over-broad**. The mechanics check out; the coverage does not. **Not cleared to build yet** — each needs
a stronger, real-pipeline test first (details + the verifier's holes in each class below).

- **`text-autosize` (427, 61%) — reposition, don't resize.**
  - *Don't derive the size offline* (`ta-derive`, measured on the deck): the `iwa_text_shape.py` TextKit
    + per-font linear height model is calibrated for AzoSans/ArgentCF; this deck is **Amplitude/
    AmplitudeCond-dominant → ~96% uncalibrated font**, plus wrap-boundary cliffs (~50px even on the
    calibrated font — a linear model can't fix a wrong line *count*) and condensed-font width (2.2×).
    Deriving size offline is intractable and the loose text verify (4px, x/y only) would HIDE the error.
  - *You don't need to* (`ta-seed`, the key finding): pass-1 JXA applies the target `fontSize` with
    geometry suppressed (`remap_keynote.py:1389`, `remap_keynote.js:240-242`), so **Keynote already
    re-grows every autosize box to its final `naturalSize` before the offline writer runs** — and the
    mandatory bulk seed already captures that grown size, then DISCARDS it because the miss check at
    `iwa_write.py:632` bails on the sentinel before `_text_fields` (already axis-safe) can use it. The
    offline pass only needs to REPOSITION.
  - *The win:* narrow `iwa_write.py:632` (it currently misses EVERY autosize box, even pure moves) +
    have the planner (`map_remap.ItemTransform.as_dict`) drop `h` for standalone autosize text →
    convert the **top-aligned** boxes (a majority on this left/top-aligned deck) to offline position
    writes, AND remove the entire fallback Keynote pass (the bulk-seed open was already paid — the real
    wall-time lever). Residue: middle/bottom-aligned boxes whose height changed. Open census tension:
    `ta-derive` measured 660 grow-both vs 123 grow-height boxes — bounds the anchor-safe fraction.
  - *Gating experiment — PASS (2026-09-17, real deck).* Offline-moved a top-anchored grow-height
    autosize box (slide 4, sentinel height, `naturalSize.h`=270.6) by +137/+91, then round-tripped
    through Keynote. Persisted geometry held exactly (Δ0.00; Keynote rewrote `Document.iwa` but left
    the slide member untouched → no re-anchor), and Keynote's **live** layout renders it at the
    written position (x=3532,y=180). Bonus: live height came back **351** vs stored 270.6 — Keynote
    re-grows autosize height at render and the top-left is unaffected, exactly as the top-anchor
    theory predicts. (Harness: `scratchpad/reanchor_{A,C}.py` + `reanchor_open.applescript`.)
  - *VERIFY CAVEAT (independent, 2026-09-17) — the mechanics are real but this DOES NOT establish
    class recovery.* The verifier confirmed Keynote genuinely re-laid-out (live h=351 is `obj.height()`,
    not a byte-echo) and the box is genuinely `kFrameAlignTop`. BUT of the 123 height-sentinel autosize
    boxes, only **11 are top-anchored; 112 are `kFrameAlignMiddle`** — the harness grabbed the first box
    and landed on the 9% minority. For middle boxes stored y is the vertical CENTRE, so the experiment's
    check (live pos == written pos) wouldn't even reproduce. Worse, the harness wrote a raw top-left,
    NOT the production `_text_fields` formula, which hard-codes "stored y is the centre" (`iwa_write.py:279-280`)
    — correct for the 112 middle boxes, WRONG for the 11 top boxes, i.e. the exact box tested. So any
    `:632` lift must branch on alignment, and the dominant middle case + the production formula are
    UNTESTED. Needed: run 3–4 middle boxes (deck-dominant font) + 2–3 top boxes through the REAL pipeline
    (pass-1 suppressed-geom read → offline reposition write → preview export) and compare the composed
    visible rect (rendered top-left AND Keynote-grown height), plus eyeball the PNG for clipping.

- **`masked-media` (188, 27%) — the crop transform already exists.**
  - `mm-crop`: the exact crop-preserving transform for ANY axis-aligned mask is already implemented and
    applied in `_masked_media_fields` (`iwa_write.py:416-426`); `_is_identity_mask` (`:382-389`) throws
    the general result away and keeps only the no-crop case. Only **rotated + anisotropic** crops are
    genuinely unwritable (would shear).
  - `mm-seed` (offline census): all 188 are true crops/rotations — tolerance-loosening and bulk-seed
    each convert ≈0. The concrete win is a sub-class: **origin-anchored crops (mask offset ≈0, ~70 of
    188)** — zero-displacement, the closest cousin of the already-verified identity case.
  - *Gating experiment — PASS (2026-09-17, real deck).* Offline-wrote a shift+scale resize on a real
    origin crop (slide 1: image showing the leftmost 25% of a 7680×1080 wall image via a 1919.8-wide
    mask at origin), applying the existing `_masked_media_fields` transform past the `_is_identity_mask`
    gate, target (200,150,1151.9,648). Offline: composed rect = target, crop fraction 0.250 preserved.
    After a Keynote round-trip: image/mask geometry **persisted** unchanged (crop not un-done) AND
    Keynote's **live** layout renders the composed frame at (200,150,1152,648) = target. (Harness:
    `scratchpad/maskcrop_{A,C}.py` + `maskcrop_open.applescript`.)
  - *VERIFY CAVEAT (independent, 2026-09-17) — CONFIRMED-WITH-CAVEATS.* Verifier confirmed `bulk_geometry`
    reports the VISIBLE masked rect (width 1152 ≈ composed, not the 4608 image frame), the crop is pure
    geometry (image frame + mask window, no hidden descriptor to desync), and `_write_natural_size` routes
    the image natural size to `originalSize` (leaving media `naturalSize` intact) so no gate self-trips.
    Two holes: (1) frame-match ≠ pixel-match — nothing checked WHICH photo region renders; a PNG export
    pixel check is still owed (risk LOW since the crop is pure geometry, but unproven — the docstring's own
    caveat, `iwa_write.py:398-401`). (2) The tested crop was origin/H at hfrac 0.25, vfrac **1.0 (no
    vertical crop)** — the dominant wall-column family (slides 6–9…), but origin/HV (7) + origin/V (3) with
    a vertical band were untested, and **offset crops (557) — the majority of masked misses — are out of
    scope entirely.** Needed: PNG pixel-verify slide 1 (leftmost-25% of the source photo) + one origin/HV
    and one origin/V crop.

- **Not researched / likely stay fundamental:** `group-needs-keynote:group-residual` (83) needs live
  layout; `group-child-scale` (6) not worth the risk; rotated/anisotropic crops; grow-both autosize text
  needing a real width change — and the census below settles the open tension: grow-both is the
  **majority (660/783, 84%)**, NOT small (`ta-derive` was right; `ta-seed`'s "most are fixed-width"
  inference from the `naturalSize.width==size.width` invariant was wrong). The reposition path still
  covers grow-both (Keynote grew the width in pass 1); only a spec that must *change* the width offline
  is stuck.

- **Recommended sequence (NOT cleared to build — stronger tests first, per the verify):**
  (1) **masked origin-crops** are the closer-to-ready lead — geometry independently confirmed; owes only a
  PNG pixel check + origin/HV+V coverage before enabling the origin case in `_is_identity_mask`/`_masked_media_fields`.
  (2) **text-autosize reposition** needs a real-pipeline test on the DOMINANT middle-anchored boxes (and
  the production `_text_fields` centre formula) before any `:632` lift — the first experiment only covered
  the 9% top-anchored minority with a non-production write path. Yield is also smaller than first claimed
  (top-anchored is 11/123 height-sentinel boxes; the middle majority may work via the existing centre
  formula but is unproven). (3) masked offset crops (557, the majority) remain a separate, larger effort.

- **Offline Amplitude-calibration side-check (2026-09-17, no Keynote — `scratchpad/amplitude_calib.py`):**
  census of the 783 autosize boxes — **97.3% uncalibrated font** (Amplitude 589 / Amplitude-Bold 108 /
  AmplitudeCond 55), **grow-height 123 vs grow-both 660**. A per-font linear fit on the grow-height
  Amplitude/Amplitude-Bold boxes reproduces Keynote's stored `naturalSize.height` to **<2.4px** (vs the
  current AzoSans-fallback's 63–80px) — but the fit is **degenerate**: it comes out `m≈0, b≈1.29`
  (≈ `1.3·fontsize`), because **0 of 112** grow-height Amplitude boxes are actually multi-line in Keynote
  (they're all one line; TextKit *over-wraps* 64/66 to 2 lines, and `m≈0` merely hides that). So
  calibration is (a) accurate here only because these boxes are single-line, (b) covers just the 123
  grow-height minority, and (c) does nothing for the 660 grow-both (width is the hard part). Verdict:
  a per-font calibration is a narrow, fragile, single-line-only win — **not a substitute for the
  reposition path**, which needs no calibration and covers both grow modes.
- **Full reports:** the four agents' findings are summarized above; scratch harness for the calibration
  side-check is `scratchpad/amplitude_calib.py`.
